# 数据中心（com.l3hub.database.wfadnf）

独立应用，用来在本机各 L3Hub 构建之间搬运数据：正式版、Canary、Nightly，以及任何沿用同一套
同步协议、只是改了包名的分支。它不依赖备份文件，全部经 ContentProvider 走 IPC。

## 为什么单独做一个应用

L3Hub 自带的版本同步要求两边数据库版本一致：增量库没有完整表结构，交给 Room 迁移会失败；
整份归档虽然能迁移，但只有「旧的往新的」一条路，返不回来。数据库版本一旦分叉，两版之间就只剩
导备份、卸载、重装、导入这一条路。

数据中心把「结构」与「数据」分开处理：结构由每个构建自己报（运行中的 `sqlite_master`），
数据由数据中心按目标结构重建。于是跨版本、跨分支都能投递，且各包的库各自留档。

## 界面

与 L3Hub 的「数据备份」页同一套排版：表达性主题（`MaterialExpressiveTheme` + 表达性动效曲线、
Android 12 以上动态取色）、可横向滚动的胶囊选项卡、一组一块的 `HubCardGroup`（组内 2dp 缝、
首尾 20dp 圆角、中间 4dp、行首 40dp 圆形图标），图标同样是 hugeicons。

L3Hub 的 `CardGroup` 在 app 模块里，依赖设置存储、Miuix 分支与毛玻璃，独立应用链接不到；数据中心的
`ui/components/HubComponents.kt` 按同一套尺寸与结构重写了一份，改两边的观感时以 app 那份为准。

四个页：

| 页 | 内容 |
| --- | --- |
| 构建 | 本机找到的构建、版本、库版本、行数与仓库占用；拉取快照、导出数据库、跳到数据库页、清空镜像 |
| 快照 | 每包最近 3 份快照；点开可以查看结构、导出 .db、回滚、删除 |
| 数据库 | 结构、会话、附件浏览（见下） |
| 同步 | 选源快照与目标构建、合并或替换、进度与日志 |

## 数据库页

数据源分两种：运行中的库与某一份快照。

- 运行中的库只走 `schema`：表名、行数、建表语句、`identity_hash` 与页大小，没有内容；
- 快照是脱离应用的一整份库，页面上所有读取都在副本上完成（只读打开），能看：

  - **结构**：每张表的行数、列名/类型/主键/非空、建表语句、索引/触发器/视图的 DDL，以及表的前 40 行；
  - **会话**：标题、更新时间、消息节点数、置顶；点开一个会话读 `message_node.messages`，按 JSON 结构
    取角色、text part 的正文与所有 part 上的 url，列出正文与引用的附件路径；
  - **附件**：`managed_files` 登记的相对路径、MIME 与大小，以及附件镜像里每个目录的文件数与占用。

会话列表最多列 300 条、附件登记最多 500 条；表数据只读前 40 行。读取失败会显示原因，不静默为空。

## 导出数据库

两种入口，都走 SAF 让用户选位置，文件名形如 `L3Hub_rikka_hub_20261121_153000.db`：

- 快照：直接复制 `rikka_hub.db`，不改动仓库里的副本；
- 运行中的库：先按普通拉取落一份快照（不带附件），再把这份快照复制出去。

导出的是裸 SQLite 库，不压缩、不打包，任何 SQLite 工具都能打开。

## 协议

协议常量在 `:syncproto`（`com.l3hub.syncproto.L3HubSyncProtocol`），应用与数据中心共用一份，
避免两边各写一套键名慢慢漂移。

在原有方法（`ping` / `export` / `job` / `import` / `manifest` / `exportDelta` / `importDelta` /
`cleanup`）之外新增一个：

| 方法 | 参数 | 返回 |
| --- | --- | --- |
| `schema` | 无 | `KEY_SCHEMA`：`PeerSchema` JSON |

`PeerSchema` 含库版本、`room_master_table.identity_hash`、页大小、体积、几张主表的行数，
以及 `sqlite_master` 里全部表 / 索引 / 触发器 / 视图的建表语句。取的是运行中的库，不是编译期导出的
schema 文件——fork 的 migrations 各自演进，导出文件未必和线上一致。

`PROTOCOL_VERSION` 保持 2：新方法只增不改，老构建收到 `schema` 会抛「未知方法」，数据中心据此
把该构建标成「只能拉、不能跨版本投递」。

## 构建发现

两条线索：包名在 `BUILD_PACKAGES` 里，或者该包导出了 `<包名>.sync` 这个 provider。

第二条不能单独当证据：ColorOS 的 `com.oplus.remotecontrol` 恰好也导出了一个同名后缀的 provider，
早期版本因此把它记成了一个 L3Hub 构建。现在的判定是：

- 已知包名照旧列出（没装也能显示「未安装」）；
- 未知包必须真的答上 `ping`，并且 `ping` 自报的 `package` 与查询的包名一致，才收进列表；
- 索引里历史遗留的、既不是已知构建又没有快照的记录，在启动加载索引时清掉（带快照的记录保留，
  那是用户的数据）。

## 调用方信任

各构建的 provider 由 UID 反查包名，允许的调用方是三个构建加数据中心
（`SyncBridge.TRUSTED_CALLERS`）。签名密钥不同，signature 级权限会把要同步的一方挡在外面，
所以只能按包名判断；包名全设备唯一，伪造只能靠改包名，那会撞掉安装。

尚未更新的 L3Hub 构建会抛 `SecurityException`，数据中心在列表里显示「需要更新到包含数据中心的版本」。

## 仓库布局

```
files/hub/
  index.json                                  元数据（各包、各快照、镜像统计）
  packages/<包名>/snapshots/<id>/rikka_hub.db 快照
  packages/<包名>/snapshots/<id>/schema.json  快照的结构（拉取时对方报的那份）
  packages/<包名>/mirror/<相对路径>            附件镜像
```

每包只留最近 3 份快照，最新的「同步前备份」始终保留。每份快照都是一整份库，1.2 GB 的库按 8 份留
就是 9.6 GB，留 3 份够回滚也够比出上一版。

## 分层备份包（协议 3）

拉取与投递从协议 3 起改用 `.l3b`（格式见 `docs/backup-bundle.md`）。

- 拉取：第一次请求 base 层（整份库），之后每次只要水位之后的增量层；拿到后套在上一份快照的副本上，
  落成新的快照。快照本身仍是一整份库——浏览、导出、回滚都依赖它，传输是增量的、存储不是。
- 投递：合并模式下第一次仍整库投递（成功后记下时刻），之后从源快照按这个水位导出一层增量，
  以 `.l3b` 投给目标，目标在下次启动时合并。结构不一致或替换模式仍走整库那条路。
- 附件与以前一致：按清单与「路径 + 字节数」的差异单独补。

水位记在每个包的记录里（`pullWatermark` / `pushWatermark`）；增量层的结构版本与上一份快照不一致、
或上一份快照已经被清理时退回整份。

## 拉取

1. `ping` 确认版本、库版本、是否有待安装数据；
2. `schema` 取结构与指纹；
3. `export`（只带数据库）→ 解出 `rikka_hub.db` → 读行数、体积、`user_version` → 落成快照；
4. 需要附件时 `manifest` 拿清单，按「本地镜像缺失或大小不同」分批 `exportDelta`（只带附件），
   单批最多 400 个文件。

重复拉取只传变化的附件；数据库每次都是整份，因为它必须包含全部表。解出来的库直接改名进快照目录，
不再复制第二份。

## 投递

结构判定不只看版本号，还看 Room 的 `identity_hash`：同一个版本号在 fork 里可能被改出不同结构。

- 结构一致：直接搬运快照里的库。
- 结构不同：以目标的建表语句重建一个空库，逐表按列名取交集抄数据。目标多出来的列用它自己的
  `DEFAULT`；没有默认值且非空时跳过整张表并在结果里报告；源里多出来的列丢弃并记录。
  消息索引 `message_fts` 连同 rowid 一起抄，`message_fts_rowid` 按抄完的索引重建，避免搜索指错会话。
  写回目标的 `identity_hash` 与 `user_version`，Room 打开时不会判定结构不符。

两种方式：

- **合并**：先把目标现状拉一份作回滚点，再把源合并进这份副本——删除墓碑先落地，对端较新的会话
  整条替换，本地缺的补进来，分组与收藏补缺，工作区与记忆按 `updated_at` 取新，用量流水只补
  本地新会话名下的。合并规则与 L3Hub 的增量合并一致。
- **替换**：目标整库换成这份快照。附件一并投递时以镜像为准，目标里多出来的附件也会清掉。

目标库是空的（七张计数表全为 0）时，合并没有可保留的东西，直接退化成整库投递：不拉回滚点，也不做
合并——省掉一次目标整库导出，以及把几万条消息重新分词进 FTS。

投递包沿用备份格式（数据库条目 `rikka_hub.db`，附件按相对路径平铺），目标侧走 `PendingRestore`
/ `PendingDelta`，在下次启动、Room 打开之前安装。合并模式先补附件、后投数据库，两个待安装目录
互不覆盖；启动顺序是先整份恢复、再增量。

## 归档不压缩

同设备内的中转，归档条目一律不压缩（app 侧 `Deflater.NO_COMPRESSION`，数据中心侧
`ArchiveTool.archiveStream`）。实测数据：

| 操作（1.2 GB 的库） | 耗时 |
| --- | --- |
| `VACUUM INTO` | 4.1 s |
| 整份复制 | 0.7 s |
| 解压 | 10 s |
| **压缩（level 6）** | **70 s**（17 MB/s） |

压缩省下 800 MB 传输（不到一秒的 I/O），却要付出一分钟 CPU；附件里的图片视频本来也压不动。
手动备份、WebDAV / S3 上传仍然压缩，那里省的是网络流量。

目标侧的导入也不做整库 `integrity_check`（`stageRestore(verify = false)`）：字节已由 zip 的 CRC
校验过，坏库仍会在 Room 打开时报出来。手动恢复与云端恢复保持校验。

## 出包

```
./gradlew :datacenter:assembleRelease
```

CI：`.github/workflows/build-datacenter.yml`，tag 形如 `DB-v1.0.0`，产物 `L3Hub-DataCenter-DB-v1.0.0.apk`
（arm64-v8a，内含应用同款的 `libsimple.so` 分词扩展），签名与 L3Hub 正式版同一把 release key。

版本号只改 `datacenter/build.gradle.kts` 的 `versionCode` / `versionName`，CI 会核对 tag 与
`versionName` 一致。

## 已知边界

- 需要目标构建先更新到含数据中心授权的版本，否则只能看到「不可用」。
- 附件镜像按「路径 + 字节数」判断是否需要重传；内容变了但大小恰好相同的文件会漏一次。
- 跨结构换算只做列级映射：字段含义变化、JSON 内部结构变化不在自动换算范围内，需在目标端手动处理。
