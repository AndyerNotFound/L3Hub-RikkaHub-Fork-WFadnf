# 备份格式：`.l3b` 与旧 zip

## 两种格式

| 格式 | 内容 | 何时用 |
| --- | --- | --- |
| `.l3b` | 分层追加容器：一个 base 层 + 若干 delta 层 | 默认 |
| `.zip` | 一整份：`settings.json` + `rikka_hub.db` + 白名单附件 | 「数据备份」页把格式切到「全量」时；旧版 L3Hub 只认它 |

`settings.json`、`rikka_hub.db`、`sync_delta.db`、`upload/…` 这些条目名两种格式一致：`.l3b`
的每一层里就是一段旧格式的 zip，base 层与一整份旧备份等价。

## 容器

```
文件  := "L3HUBBND1" record*
record := "L3B1" | headerLen u32 | header JSON | payloadLen u64 | payload
payload := zip（rikka_hub.db / sync_delta.db / settings.json / 附件）
```

头部是一个 JSON 对象，字段见 `BundleFormat.Layer`：层类型（`base` / `delta`）、生成时刻、水位
`since`、库结构版本、设备标识、是否带数据库、设置指纹、本层携带的附件与声明删除的附件。

- 追加是纯字节追加，前面写好的记录不重写；
- 尾部半截记录（断电、上传中断）读取时丢弃，下次追加前按有效长度截断；
- 远端不能原地追加，所以 WebDAV / S3 上一个备份集是「`backup_x.l3b` + `backup_x.l3b.d001`
  + …」多个对象：链首带文件头，其余是裸记录，恢复时按顺序拼成一份完整的包。

## 增量层里有什么

增量层是 `SyncDelta` 的产物，按会话 `update_at` 的水位切：整条会话与其消息节点、搜索行、删除墓碑、
记忆、工作区、附件登记、媒体创作、用量流水，加上这一段时间变化或新增的附件。没有时间戳的小表
（分组、收藏）整表带上。

链上声明删除的附件记在 `deletedFiles`：覆盖方式恢复会清掉备份里没有的文件，合并方式保留本地的。

## 什么时候重开一条链

出现任一条就写一个新的 base 层（旧链从此不再使用）：

- 目标上没有可接的链，或本地链状态丢了（换机、清数据、换备份目录）；
- 库结构版本变了；
- 这次带不带数据库与链首不同；
- 链已经有 10 层，或链首超过 7 天；
- 链首属于别的设备。链只属于一台设备的一条结构版本，混着接会静默丢数据。

远端备份集每次追加前都会核对链首对象还在不在：被删掉就重开一条链，本地状态作废。

## 恢复

1. 取最后一条完整的链（最后一个 base 到末尾）；
2. base 层的库落到待安装目录，后面的 delta 层按顺序打进这份副本（同一套增量合并 SQL）；
3. 设置取最后一个带设置的层；附件逐层覆盖；
4. 之后走与整份恢复完全相同的收尾：完整性校验、Room 迁移、附件路径改写、SSH 凭据清理，
   在下次启动、Room 打开之前安装。

没有 base 层的纯增量包（别的构建或数据中心投递过来的）不进这条路：它落到增量待安装目录，
启动时直接合并进现有库。

## 水位与设备身份

- 水位取上一层创建时刻往前让两秒：导出期间正在写入的会话宁可下次多带一遍，也不漏掉；
- 增量合并本身是幂等的，重复应用同一层不会产生第二份数据；
- 设备身份存在应用私有目录的偏好里，只用于决定能不能接着追加。

## 兼容

- 旧 zip 的恢复路径一行未改，`.l3b` 只是把它多包了一层；
- 协议 2 的构建之间仍按原来的增量 zip 互换；协议 3 起新增 `exportBundle`，两个构建之间与数据中心
  都改走 `.l3b`，接收侧按文件头识别格式，旧构建收到会当作未知方法失败，调用方据此降级。
